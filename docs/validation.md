# Validation

## 1. Purpose

Data Career Copilot combines deterministic rules, LLM-based semantic interpretation, structured outputs and rule-based scoring.

Because the system contains both deterministic and probabilistic components, validation cannot rely on a single metric.

The validation strategy therefore evaluates the system at multiple levels:

```text
Component Validation
        ↓
Behavioral / Regression Validation
        ↓
End-to-End Validation
```

The objective is to answer three different questions:

1. Does the deterministic relevance classifier behave as expected?
2. Do important matching and scoring rules produce the intended behavior?
3. Can the complete workflow execute successfully from job discovery to prioritized notification?

This document summarizes the evidence collected during development.

---

## 2. Validation Scope

The current validation covers three layers.

| Validation Layer | Objective |
|---|---|
| Relevance Filter | Measure initial classification behavior |
| Matching & Scoring | Verify important decision rules and edge cases |
| End-to-End Workflow | Verify the complete production pipeline |

These layers should not be interpreted as equivalent.

For example, a successful end-to-end execution proves that the pipeline can operate as designed, but it does not by itself measure the accuracy of every recommendation.

Similarly, the manually labeled Relevance Filter benchmark measures one component of the system, not the performance of the entire Career Copilot.

---

# 3. Component Validation — Relevance Filter

## 3.1 Evaluation Dataset

The first version of the deterministic relevance classifier was evaluated using a manually reviewed sample of:

```text
50 job postings
```

Each vacancy was labeled according to whether it should continue through the Data Career Copilot pipeline.

The manually assigned labels were then compared with the predictions generated by Relevance Filter V1.

---

## 3.2 Confusion Matrix

The evaluation produced:

| | Manually Relevant | Manually Not Relevant |
|---|---:|---:|
| **Filter Relevant** | 44 TP | 4 FP |
| **Filter Not Relevant** | 1 FN | 1 TN |

Where:

- **TP — True Positive:** relevant vacancy correctly retained
- **FP — False Positive:** irrelevant vacancy incorrectly retained
- **FN — False Negative:** relevant vacancy incorrectly rejected
- **TN — True Negative:** irrelevant vacancy correctly rejected

---

## 3.3 Metrics

### Precision

```text
Precision = TP / (TP + FP)

Precision = 44 / 48

Precision ≈ 91.7%
```

### Recall

```text
Recall = TP / (TP + FN)

Recall = 44 / 45

Recall ≈ 97.8%
```

### F1 Score

```text
F1 ≈ 94.6%
```

Summary:

| Metric | Result |
|---|---:|
| Sample size | 50 |
| True Positives | 44 |
| True Negatives | 1 |
| False Positives | 4 |
| False Negatives | 1 |
| Precision | 91.7% |
| Recall | 97.8% |
| F1 Score | ~94.6% |

These results correspond specifically to:

```text
Relevance Filter V1
+
the evaluated 50-job sample
```

They are not presented as universal production-performance estimates.

---

## 3.4 Why Recall Matters

The Relevance Filter is positioned before the more expensive AI analysis stages.

A false positive causes an irrelevant vacancy to consume additional downstream resources.

A false negative has a different consequence:

```text
Potentially valuable vacancy
        ↓
Rejected by prefilter
        ↓
Never reaches candidate matching
```

For this reason, the system intentionally prioritizes maintaining high recall while still removing obvious noise.

The observed V1 recall of approximately 97.8% was therefore particularly useful as an initial baseline.

# 4. Error Analysis

Metrics alone were not sufficient to refine the filter.

Individual errors were inspected to identify generalizable classification problems.

Three cases were particularly useful.

---

## 4.1 Banorte

Observed diagnostic behavior:

```text
relevance_score: 3
pillars: 1
```

The vacancy did not provide enough evidence to justify deeper processing.

This case reinforced the need to require sufficient supporting signals rather than allowing isolated analytical terminology to determine relevance.

---

## 4.2 Seguros Monterrey

This vacancy contained several Data-related signals but its central function was more closely related to:

```text
Machine Learning / Data Science
```

rather than the primary job families targeted by the project.

This revealed a limitation in the original classification strategy:

> A vacancy can contain relevant technologies and analytical terminology while still belonging to a non-priority technical function.

The resulting V1.1 refinement introduced a functional ML / Data Science blocker that requires multiple explicit signals before classifying the role as primarily ML / Data Science.

---

## 4.3 Zincro

Zincro exposed the opposite problem.

The job title was ambiguous and could be interpreted as a generic Functional Analyst position.

However, the vacancy contained meaningful evidence related to:

```text
Data
+
Automation
+
Business Processes
```

Observed diagnostic behavior included:

```text
relevance_score: 5
pillars: 1
hybrid_data_automation_role: true
```

This case contributed to the introduction of a hybrid Data + Automation path in V1.1.

It also demonstrated why increasing the global relevance threshold could unintentionally reject valuable hybrid opportunities.

---

# 5. V1 → V1.1 Validation Status

The V1 evaluation led to several improvements in V1.1, including:

- improved treatment of ambiguous Functional Analyst roles
- hybrid Data + Automation detection
- functional ML / Data Science blocking
- additional diagnostic information

However, an important distinction is maintained:

> The Precision, Recall and F1 metrics reported in this repository belong to the V1 baseline.

V1.1 has been tested during workflow development and through targeted regression cases, but it has not yet been evaluated against a new sufficiently large manually labeled benchmark.

Therefore, this project does **not** claim that V1.1 has:

```text
91.7% Precision
97.8% Recall
94.6% F1
```

Those metrics remain historical V1 benchmark results.

A future controlled evaluation should measure V1.1 independently.

# 6. Behavioral Validation — Matching & Scoring

The matching and scoring system was validated differently from the Relevance Filter.

Rather than treating a small number of manually inspected vacancies as a statistical accuracy benchmark, selected vacancies were used as **behavioral and regression cases**.

The objective was to verify whether important rules behaved as intended.

These cases tested situations involving:

- strong overall compatibility
- partial compatibility
- missing core technologies
- language requirements
- academic requirements
- geographic constraints
- hybrid Data + Automation roles

---

## 6.1 Positive Control — Kuna Capital

Observed result:

```text
Final Score: 97
Recommendation: Apply
```

This vacancy served as a positive-control case for strong candidate-to-vacancy alignment.

The result demonstrated that the scoring system could preserve a high score when the structured evaluation showed strong compatibility and no major structural blocker required a cap.

---

## 6.2 Intermediate Case — YouTube

Observed result:

```text
Final Score: 72
Recommendation: Review
```

This case helped validate the intermediate recommendation range.

The vacancy contained meaningful compatibility but not enough evidence to reach the Apply threshold.

---

## 6.3 Intermediate Case — CS Servicios

Observed result:

```text
Final Score: 69
Recommendation: Review
```

This provided an additional regression case around the middle scoring range.

It helped verify that partial alignment remained visible without automatically promoting the vacancy to Apply.

---

## 6.4 Structural Gaps — Ultimate Jet

Observed result:

```text
Final Score: 59
Recommendation: Discard
```

Important gaps identified during evaluation included:

- English
- Tableau
- academic background

This case was useful because it showed how structural requirements can materially affect the final result even when other aspects of a vacancy appear relevant.

---

## 6.5 Geographic Constraint — Zincro

Observed result:

```text
Final Score: 59
Recommendation: Discard
```

The vacancy had meaningful Data + Automation relevance.

However, candidate-specific geographic constraints reduced its practical compatibility.

This case validates the separation between:

```text
Job Relevance
```

and:

```text
Candidate Compatibility
```

A vacancy can correctly pass the Relevance Filter while still receiving a low final recommendation.

---

# 7. Rules Tested Through Regression Cases

The behavioral validation process helped verify several important system rules.

## Relevant Experience vs Total Experience

The candidate has more than eight years of total professional experience.

The system must not automatically interpret this as:

```text
8+ years of Data experience
```

Matching therefore evaluates relevant analytical and technical evidence separately.

---

## Skill Presence vs Skill Level

Having a technology in the candidate profile is not sufficient to satisfy every requirement involving that technology.

For example:

```text
Intermediate Python
```

does not automatically satisfy:

```text
5+ years of advanced Python development
```

---

## Alternative Technologies

Requirements such as:

```text
Power BI or Tableau
```

are treated as alternatives when the vacancy clearly expresses them that way.

Demonstrating one valid alternative can satisfy the technology group.

---

## Explicit Exclusionary Requirements

An exclusionary condition is activated only when:

```text
Vacancy explicitly requires condition
+
Candidate profile explicitly demonstrates that condition is not met
```

Missing candidate information alone is not treated as proof of failure.

---

## Geographic Constraints

The matching system preserves the candidate's actual work-location constraints.

The intended behavior is:

```text
On-site outside CDMX / Estado de México
→ Not compatible

Hybrid requiring attendance outside CDMX / Estado de México
→ Not compatible

Remote from Mexico
→ Compatible

Outside allowed geography + modality unknown
→ Partial / uncertain
```

This prevents the system from assuming willingness to relocate.

---

# 8. Deterministic Scoring Validation

The scoring engine is implemented separately from the LLM.

The model returns structured qualitative compatibility dimensions.

JavaScript then applies:

```text
Weights
+
Critical requirement penalties
+
Core technology caps
+
Exclusionary caps
+
Recommendation thresholds
```

This separation allows deterministic scoring rules to be inspected independently from the semantic interpretation layer.

---

## 8.1 Weight Validation

The scoring weights total 100 points:

| Dimension | Weight |
|---|---:|
| Related Experience | 25 |
| Tools & Technologies | 25 |
| Responsibilities | 15 |
| Industry / Context | 10 |
| Seniority | 10 |
| Language | 5 |
| Modality & Location | 5 |
| Salary | 5 |
| **Total** | **100** |

The sum can therefore be verified directly:

```text
25 + 25 + 15 + 10 + 10 + 5 + 5 + 5 = 100
```

---

## 8.2 Critical Requirement Penalty

The current rule is:

```text
critical_penalty =
min(number_of_missing_critical_requirements × 3, 12)
```

This ensures that:

- each critical gap has a measurable impact
- the penalty cannot grow indefinitely

---

## 8.3 Core Technology Caps

The expected behavior is:

| Missing Core Technologies | Maximum Score |
|---|---:|
| 0 | No additional cap |
| 1 | 79 |
| 2 | 69 |
| 3+ | 59 |

These caps ensure that strong performance in unrelated dimensions cannot fully compensate for several technologies that are central to performing the role.

---

## 8.4 Exclusionary Cap

When a confirmed exclusionary requirement exists:

```text
Maximum Final Score = 59
```

This keeps the result below the Review threshold.

---

## 8.5 Recommendation Thresholds

The final score is classified as:

```text
80–100 → Apply
60–79  → Review
0–59   → Discard
```

The recommendation layer is therefore deterministic once the final score has been calculated.

One validated production execution produced:

```text
47 new vacancies
```

The final classification was:

| Recommendation | Vacancies |
|---|---:|
| Apply | 9 |
| Review | 7 |
| Discard | 31 |
| **Total** | **47** |

The arithmetic consistency can be verified:

```text
9 + 7 + 31 = 47
```

The notification layer surfaced:

```text
9 Apply
+
7 Review
=
16 prioritized opportunities
```

The remaining:

```text
31 Discard
```

vacancies were counted but were not expanded into detailed recommendation cards in the final email.

---

# 11. End-to-End Behaviors Verified

The successful execution confirmed that the workflow could:

- generate multiple job-search queries
- retrieve vacancies through SerpApi
- normalize source data
- generate vacancy hashes
- apply deterministic relevance filtering
- compare results against existing CRM records
- avoid processing known vacancies again
- process relevant vacancies sequentially
- extract structured job requirements with an LLM
- retrieve the candidate profile from Google Sheets
- evaluate semantic compatibility
- calculate deterministic compatibility scores
- generate vacancy identifiers
- persist results into the CRM
- isolate records belonging to the current execution
- generate a prioritized execution summary
- send the final summary through Gmail

This validates the integration of the complete V1 pipeline.

---

# 12. What the Full Execution Does Not Prove

A successful production run is important evidence, but its meaning should not be overstated.

The result:

```text
9 Apply
7 Review
31 Discard
```

does **not** prove that every classification was objectively correct.

It proves that:

> The complete system executed successfully and produced internally consistent outputs according to the implemented rules.

Determining recommendation accuracy at scale would require additional labeled candidate-vacancy pairs and potentially downstream application outcomes.

---

# 13. Validation Boundaries

The current project has not yet established:

### V1.1 Relevance Filter performance

A new manually labeled benchmark is required.

### Recommendation accuracy

Apply / Review / Discard classifications have been inspected through selected cases but have not been evaluated against a large independent labeled dataset.

### Real-world application conversion

The system does not yet measure whether:

```text
Apply
→ Recruiter Response
→ Interview
→ Offer
```

occurs more frequently for higher-scoring vacancies.

### Long-term model stability

LLM outputs can change because of:

- model updates
- prompt modifications
- differences in vacancy descriptions

Regression testing remains important.

# 15. Future Validation Strategy

The next validation stage should focus on building a larger evaluation dataset.

A stronger process could use:

```text
Historical Vacancies
        ↓
Manual Ground Truth
        ↓
Automated Pipeline Evaluation
        ↓
Prediction vs Ground Truth
        ↓
Metrics
        ↓
Error Analysis
        ↓
Regression Dataset
```

For the Relevance Filter, this would enable updated:

- Precision
- Recall
- F1 Score
- confusion matrix

For candidate matching, future labeled data could evaluate whether human judgments agree with:

- Apply
- Review
- Discard

recommendations.

# 16. Outcome-Based Validation

The strongest future validation would use actual job-search outcomes.

For example:

```text
Vacancy
   ↓
Compatibility Score
   ↓
Application
   ↓
Recruiter Response
   ↓
Interview
   ↓
Technical / Hiring Stage
   ↓
Offer / Rejection
```

With sufficient observations, the project could evaluate:

- response rate by score range
- interview rate by recommendation
- technologies associated with rejection
- recurring skill gaps
- job families with higher conversion
- whether scoring weights require recalibration

This would transform the current rule-based validation framework into a data-driven career feedback loop.

---

# 17. Validation Principles

The project follows several validation principles.

**Do not confuse execution success with prediction accuracy**

A workflow can execute correctly while still producing incorrect classifications.

**Do not transfer metrics between versions**

V1 metrics are not automatically V1.1 metrics.

**Use labeled examples when measuring classification**

Quantitative metrics require a reference ground truth.

**Use regression cases for important business rules**

Specific cases are useful for verifying expected behavior even when they do not constitute a statistical benchmark.

**Preserve uncertainty**

Missing information should not be converted into unsupported certainty.

**Avoid overfitting**

Individual errors should lead to new rules only when they reveal a generalizable pattern.

**Validate outcomes when they become available**

The long-term quality of the system should ultimately be evaluated using real application outcomes.

# 18. Summary

The current Data Career Copilot V1 has been validated at three levels:

```text
1. COMPONENT
   Relevance Filter V1
   → 50 manually labeled vacancies
   → Precision: 91.7%
   → Recall: 97.8%
   → F1: ~94.6%

2. BEHAVIORAL
   Matching & Scoring
   → Selected regression cases
   → Compatibility rules
   → Constraints
   → Penalties and caps

3. END-TO-END
   Complete workflow
   → 47 new vacancies
   → 9 Apply
   → 7 Review
   → 31 Discard
   → 16 prioritized opportunities
```

This evidence demonstrates that the V1 system is operational and that its main decision rules have been tested.

At the same time, the project deliberately avoids presenting limited validation results as universal performance guarantees.

The next maturity step is to expand the labeled evaluation dataset and connect recommendation scores with real application outcomes.
